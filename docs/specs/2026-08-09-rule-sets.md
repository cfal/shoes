# Rule-sets: design

Status: approved, not implemented
Date: 2026-08-09
Tracks: [ROADMAP.md](../../ROADMAP.md) Tier 1, item 1

## Problem

`masks` is a literal list of CIDRs and `*.domain` wildcards. Expressing a rule as
ordinary as "Russian domains direct, everything else through the tunnel" would
take tens of thousands of YAML lines, so in practice nobody writes it. The
routing engine is unusable for a real client, and that blocks the value of the
rest of the Tier 1 work.

sing-box's `.srs` container is a documented binary format with a large ecosystem
of pre-compiled lists behind it (geosite, geoip, antifilter, Loyalsoldier).
Reading it directly means those lists work on day one, with no list-building
pipeline of our own.

## Scope

In scope for v1:

- Loading rule-sets from local `.srs` files, format versions 1 through 5.
- Matching on `domain`, `domain_suffix`, `domain_keyword`, `domain_regex` and
  `ip_cidr`.
- Decoding `source_ip_cidr`, and rejecting any rule-set that uses it. See
  "Source addresses" below.
- Referencing rule-sets from routing rules, OR-combined with `masks`.
- Reloading when a `.srs` file changes, for the `shoes` binary.

Out of scope for v1, each a separate piece of work:

- Remote rule-sets (`url`, `update_interval`, download through a proxy chain,
  on-disk cache). The mobile client already downloads files; it can own this
  until we need it in the core.
- Inline rule definitions in YAML.
- `type: logical` rules, the AdGuard domain matcher, and every matcher that
  needs context we do not have: `process_name`, `package_name`, `network_type`,
  `wifi_ssid`, and the interface-address family.
- `rule_set_ip_cidr_match_source`. v1 always treats `ip_cidr` as a destination
  matcher and `source_ip_cidr` as a source matcher.

## Evidence

Twelve published rule-sets were downloaded and decoded to validate the format
understanding before this design was written. Every file parsed cleanly to its
final marker.

| File | Contents |
| --- | --- |
| `geoip-ru.srs` | `ip_cidr` (9551 ranges) |
| `geoip-us.srs` | `ip_cidr` (31543 ranges) |
| `geosite-apple.srs` | `domain` (20310 B labels) |
| `geosite-cloudflare.srs` | `domain` (1082 B labels) |
| `geosite-microsoft.srs` | `domain` (8236 B labels) |
| `geosite-telegram.srs` | `domain` (221 B labels) |
| `geosite-youtube.srs` | `domain` (2191 B labels) |
| `geosite-google.srs` | `domain` (9454 B), `domain_regex` (2) |
| `geosite-netflix.srs` | `domain` (341 B), `domain_regex` (4) |
| `geosite-openai.srs` | `domain` (379 B), `domain_regex` (1) |
| `geosite-category-ads-all.srs` | `domain` (8801 B), `domain_regex` (1) |
| `geosite-category-porn.srs` | `domain` (56567 B), `domain_regex` (140) |

Four conclusions drive the design:

1. **`domain_regex` appears in five of ten geosite sets**, including google,
   netflix, openai and the ads list. A build without regex support that also
   fails loudly on unsupported items would refuse to load half the popular
   lists, so regex is in scope.
2. **`domain_keyword` appears in none of them**, and neither do logical rules or
   `invert`. `domain_keyword` and `invert` are implemented anyway — each is a
   handful of lines, and absence from a twelve-file sample is not a guarantee.
   Logical rules are rejected, being neither cheap nor observed.
3. **Every file contains exactly one rule.** Multi-rule sets are supported
   anyway; the format allows them.
4. **Memory is not a constraint.** The largest domain trie is 56 KB of labels
   and the largest IP set inflates to 688 KB. Against the ~50 MB iOS
   packet-tunnel budget that MOBILE.md identifies as the blocking constraint,
   this is noise — provided the trie is kept in its on-disk shape rather than
   expanded into strings.

## Binary format

```
file        := "SRS" | version:u8 | zlib(payload)
payload     := uvarint(rule_count) | rule*
rule        := rule_type:u8 | body            ; 0 = default, 1 = logical
default     := item* | 0xFF | invert:u8
```

Helper encodings:

```
uvarint     := LEB128, unsigned
u64slice    := uvarint(n) | n × u64 big-endian
byteslice   := uvarint(n) | n bytes
strlist     := uvarint(n) | n × (uvarint(len) | len bytes, UTF-8)
```

Item types we decode:

| Tag | Name | Encoding |
| --- | --- | --- |
| `0x02` | `domain` | `set_version:u8` (must be 0), `u64slice` leaves, `u64slice` label_bitmap, `byteslice` labels |
| `0x03` | `domain_keyword` | `strlist` |
| `0x04` | `domain_regex` | `strlist` |
| `0x05` | `source_ip_cidr` | IP set |
| `0x06` | `ip_cidr` | IP set |
| `0xFF` | final | `invert:u8`, ends the rule |

IP set encoding, noting that the count is a fixed-width big-endian `u64` rather
than a uvarint:

```
ip_set      := set_version:u8 | count:u64 big-endian | range × count
range       := uvarint(len) | len bytes | uvarint(len) | len bytes
```

`set_version` must be 1. Each address is 4 or 16 bytes, in `netip.Addr` binary
form; any other length is an error. The two addresses of a range are its
inclusive lower and upper bound.

The domain matcher encoding is identical across all format versions. Version 1
differs only in what the *compiler* puts into the set, which does not affect
reading.

sing-box reads both `set_version` bytes and discards them. We require them to
hold their current values instead. That is stricter, and it is the intended
behaviour: an unrecognised encoding should stop the load rather than be silently
misread as the one we know.

Item tags `0x00`, `0x01` and `0x07` through `0x17` are known but unsupported;
they are named in the error message rather than skipped, because their payload
lengths differ and skipping them would desynchronise the stream.

## Matching semantics

Taken from `route/rule/rule_abstract.go` in sing-box, where items are bucketed
into groups, `matchAnyItem` runs within a group, and the groups are then ANDed.
`ip_cidr` joins the *destination address* group, the same one the domain
matchers are in — so it ORs with them rather than ANDing.

```
rule matches   ⟺   dest_group ⊕ invert

dest_group     = domain ∨ domain_keyword ∨ domain_regex ∨ ip_cidr

A group with no items is not required and does not participate.
A rule with no items at all matches everything, and ignores invert.

RuleSet matches ⟺ any of its rules matches.
```

The source group is absent because `source_ip_cidr` is rejected at load; see
below.

Getting this wrong in the obvious direction — ANDing `domain` with
`domain_regex` — would make `geosite-google` match almost nothing, and would be
hard to notice. The dedicated test in the plan exists for this.

### Domain normalisation

Before matching, the destination hostname is lowercased (ASCII) and a single
trailing dot is stripped. Published lists are lowercase and DNS labels are
case-insensitive.

This is deliberately different from the existing `matches_domain`
(`src/client_proxy_selector.rs:404`), which is case-sensitive. The divergence is
scoped to rule-sets; changing mask behaviour is not part of this work.

### Source addresses

`ClientProxySelector::judge` takes a destination and a resolver. The client's own
address is not in scope at that point and is not plumbed through to it, so a
`source_ip_cidr` matcher has nothing to compare against.

The parser therefore decodes `source_ip_cidr` — leaving a hole in the decoder
would desynchronise the stream — but building a `RuleSet` from a rule that
carries one is a load error naming the field. Accepting it and always returning
false would be a rule-set that silently never matches, which is exactly the
failure mode the fail-loud policy exists to prevent.

Supporting it means plumbing the source address into `judge`, which is its own
change and is not part of this work.

### Hostname destinations and IP matchers

When the destination is a hostname and a rule-set matches only on `ip_cidr`,
whether to resolve is governed by the **existing `resolve_rule_hostnames` flag**
(`src/client_proxy_selector.rs:197`). No second flag is introduced. A rule-set
should behave like another mask, not like a separate subsystem with its own
rules.

## Module layout

New `src/rule_set/`, one responsibility per file:

| File | Responsibility | Depends on |
| --- | --- | --- |
| `srs.rs` | container parsing: magic, version, zlib, uvarint, TLV items | `flate2` |
| `succinct.rs` | succinct trie: rank/select, `has()`, domain reversal | — |
| `ip_set.rs` | sorted `[from, to]` ranges, binary search | — |
| `rule.rs` | `HeadlessRule` and the group semantics above | `regex-lite` |
| `mod.rs` | `RuleSet`, file loading, the name registry | all of the above |

`succinct.rs` and `ip_set.rs` know nothing about `.srs`; `srs.rs` knows nothing
about matching. Each is unit-testable on its own.

## Data structures

The succinct trie is held in its on-disk shape:

```rust
pub struct DomainMatcher {
    leaves: Vec<u64>,
    label_bitmap: Vec<u64>,
    labels: Vec<u8>,
    ranks: Vec<i32>,    // rebuilt on load; not serialised
    selects: Vec<i32>,  // rebuilt on load; not serialised
}
```

`ranks` is a per-word prefix popcount with a trailing total. `selects` samples
the position of every 32nd set bit in `label_bitmap`.

sing-box implements `selectIthOne` with a 2 KB `select8Lookup` table and nested
byte-width popcounts. Porting that verbatim is unnecessary: starting from the
sampled `selects` entry and scanning forward word by word with `count_ones` and
`trailing_zeros` gives identical results in roughly forty lines. Rule-set
matching sits behind the existing `RoutingCache` LRU, so the constant factor
does not matter.

Lookup, ported from `Matcher.has`:

- `PREFIX_LABEL = b'\r'` marks a suffix match, `ROOT_LABEL = b'\n'` marks a
  label-boundary suffix match.
- The key is the domain **reversed by character, not by byte**. Go reverses runes
  and re-encodes them; `s.chars().rev().collect::<String>()` is exactly
  equivalent, and is safe because Rust hostnames are already valid UTF-8. The
  reversed key is then walked byte by byte.

IP sets:

```rust
pub struct IpSet {
    ranges: Vec<(u128, u128)>,  // inclusive, in file order (already sorted)
}
```

Lookup is `partition_point` over `ranges`. IPv4 addresses are converted to
IPv4-mapped form, matching `ip_to_u128` (`src/client_proxy_selector.rs:386`).
The sortedness of the file's ranges is verified once at load; an unsorted file
is a load error rather than a silently wrong matcher.

## Configuration

Declaration is a top-level entry, following the existing `client_group`,
`rule_group`, `dns_group` and `pem` idiom. Reference is a `rule_sets` field
inside a rule, OR-combined with `masks`.

```yaml
- rule_set: geosite-ru
  path: /etc/shoes/geosite-ru.srs

- rule_set: geoip-ru
  path: /etc/shoes/geoip-ru.srs

- address: 0.0.0.0:1080
  protocol: {type: socks}
  rules:
    # matches on any mask OR either rule-set
    - masks: ["192.168.0.0/16", "*.local"]
      rule_sets: [geosite-ru, geoip-ru]
      action: allow
      client_chain: {protocol: {type: direct}}

    - masks: "0.0.0.0/0"
      action: allow
      client_chain: my-proxy
```

`rule_sets` accepts a single string or a list, matching how `masks` and
`client_chain` already behave.

**Discriminator ordering.** `Config`'s deserialiser
(`src/config/types/groups.rs:199`) picks a variant by which fields are present,
and `path` is already claimed by a Unix-socket `ServerConfig`. The `rule_set`
check must come **before** the `has_address || has_path_field` branch, or
`- rule_set: … / path: …` will be routed to the server parser and fail with an
unrelated message. The final `else` branch's help text gains a line for the new
type.

Paths are resolved relative to the directory of the config file that declared
them, so a config directory can be relocated intact. `load_configs`
(`src/config/mod.rs:27`) already iterates per file and is the only place that
still knows which file a config entry came from, so resolution happens there.
`load_config_str`, the FFI entry point, has no such path; a relative path from
that path is left untouched and resolves against the process working directory.

## Integration

`ConnectRule` (`src/client_proxy_selector.rs:114`) gains a field:

```rust
pub struct ConnectRule {
    pub masks: Vec<NetLocationMask>,
    pub rule_sets: Vec<Arc<RuleSet>>,
    pub action: ConnectAction,
}
```

`match_rule` (`src/client_proxy_selector.rs:422`) tries the masks for a rule as
it does today, and on no match tries that rule's rule-sets before moving to the
next rule. Masks first is deliberate: they are cheaper and usually more
specific.

Rule-sets are `Arc`-shared. Several server configs may reference the same set,
and it is parsed once. The name-to-`Arc` registry is built during config
expansion, alongside the existing group resolution in `ConfigSelection`
(`src/config/types/selection.rs`).

`CACHE_RULE_THRESHOLD` (`src/client_proxy_selector.rs:187`) decides whether the
`RoutingCache` is enabled at all. Any rule carrying a rule-set forces the cache
on, regardless of rule count: a set is unconditionally more expensive to
evaluate than a handful of masks.

## Error handling

Everything about loading is a configuration error, surfaced before the process
starts serving and caught by `--dry-run`:

- file missing or unreadable
- magic is not `SRS`
- version greater than 5
- malformed zlib stream, or trailing bytes after it
- truncated stream at any point
- unknown item tag
- known but unsupported item tag — named, with the rule index
- `source_ip_cidr`, which decodes but cannot be evaluated
- `type: logical` rule
- `set_version` other than the expected constant, for either the domain matcher
  or an IP set
- IP address of a length other than 4 or 16
- IP set ranges out of order
- `domain_regex` pattern that fails to compile — reported with the pattern
- `rule_sets` naming a rule-set that was never declared
- two top-level entries declaring the same `rule_set` name

Matching itself cannot fail. It returns a boolean.

## Reloading

`start_notify_thread` (`src/main.rs:80`) currently watches only the config paths
passed as arguments. It gains the `.srs` paths discovered during config loading,
so editing or replacing a rule-set file triggers the same reload path a config
edit does.

The FFI entry points have no watcher at all, so on mobile reloading stays the
host application's responsibility. This is a property of the existing design,
not something this work changes.

## Testing

- **Reference vectors.** `common/domain/matcher_test.go` and
  `set_compat_test.go` in sing provide domain-list to expected-match pairs.
  These are transcribed as the correctness baseline for `succinct.rs`.
- **Golden files.** Six of the rule-sets above — google, telegram, cloudflare,
  category-ads-all, geoip-ru and geoip-us — are committed under
  `tests/data/rule_sets/` and asserted to parse and to match known members. The
  six cover every shape the evidence table shows: a pure domain trie, a trie
  with regexes alongside it, and a pure IP set, at both small and large sizes.
- **Round-trip property.** For a set whose domain list is known, every listed
  domain matches and `<domain>.example.invalid` does not.
- **Group semantics.** A rule carrying both `domain` and `ip_cidr` matches a
  destination hitting either one. This is the test that would have caught the
  AND/OR mistake described above.
- **Normalisation.** `EXAMPLE.COM`, `example.com.` and `example.com` all match
  the same entry.
- **Rejection cases.** Truncated file, wrong magic, version 99, unknown item
  tag, unsupported item tag, logical rule, uncompilable regex, unsorted IP set —
  each asserted to produce its own message.
- **Integration.** A config referencing two rule-sets routes a destination in
  one of them through the expected chain, and a destination in neither through
  the fallback rule.

Committing roughly 255 KB of `.srs` fixtures is a deliberate trade: these files
are the specification of the format in practice, and a parser for a
reverse-engineered binary format without real inputs in the test suite is not
meaningfully tested.

## Dependencies

Two new runtime dependencies:

- `flate2` with `default-features = false, features = ["rust_backend"]`. The
  pure-Rust backend avoids adding a C toolchain requirement to the Android and
  iOS cross-builds.
- `regex-lite`, roughly 100 KB, pure Rust, no Unicode tables, linear-time
  matching and therefore no ReDoS exposure. The full `regex` crate costs about
  1.5 MB, which MOBILE.md's size constraints do not justify for at most a few
  hundred patterns sitting behind an LRU cache.

`regex` currently appears in `Cargo.lock` but is not a runtime dependency —
`cargo tree -i regex -e normal` is empty, so it arrives only through the build
graph. Adding `regex-lite` does not change that.
